### Q044（原始编号: 14）

**【题干】**
缓存能用在哪些场景？

**【核心结论】**
适合读多写少、允许短暂不一致或可重建的数据：热点查询、会话、分布式锁、限流计数、排行榜、验证码等；不适合强一致且难重建的唯一权威数据（除非有完善一致性方案）。

**【详细说明】**
场景分类：
1. 数据库热点行/配置字典。
2. Session / Token。
3. 接口幂等键、短时验证码。
4. 分布式锁、限流（令牌桶计数）。
5. 排行榜（ZSet）、布隆过滤器辅助。
6. 页面片段或对象级缓存（注意失效）。
原则：命中率、穿透防护、过期与更新策略。

**【示例/写法】**
用户资料：DB 为源，Redis String/Hash + TTL；更新时删除缓存。

**【易错点】**
- 把强一致库存只放缓存当权威。

**【权威依据】**
- Redis 官方 Use Cases；缓存模式（Cache-Aside 等）经典论述

### Q045（原始编号: 15, 121, 236）

**【题干】**
缓存击穿的原因以及解决办法。

**【核心结论】**
缓存击穿：热点 key 过期瞬间大量请求打到 DB。解决：互斥重建（分布式锁）、逻辑过期、永不过期+异步刷新、多级缓存。

**【详细说明】**
与穿透、雪崩区分：
- 击穿：单个热点过期。
- 穿透：查询不存在的数据，缓存与 DB 皆无。
- 雪崩：大量 key 同时过期或缓存宕机。
击穿手段：
1. 获锁的线程查 DB 回填，其它等待或降级。
2. value 存逻辑过期时间，过期仍返回旧值并异步刷新。
3. 热点 key 不设 TTL 或 TTL 打散 + 定时续期。

**【示例/写法】**
if (cache miss) {
  if (tryLock(key)) { loadDB(); setCache(); unlock(); }
  else { sleep/retry or return stale; }
}

**【易错点】**
- 把穿透方案（布隆）当成击穿唯一解。

**【权威依据】**
- 业界缓存三问题通识；Redis 文档（锁、过期）

### Q047（原始编号: 32, 183）

**【题干】**
Redis 怎么保证数据一致性？

**【核心结论】**
Redis 与 DB 之间通常是最终一致：常用 Cache-Aside（先更新 DB 再删缓存）、延迟双删、订阅 binlog 删缓存；强一致需慎重（锁+单写路径）。Redis 主从是异步复制，有丢失窗口。

**【详细说明】**
1. 应用与 DB：
   - Cache-Aside：读 miss 装载；写更新 DB 后删除缓存（而非先改缓存）。
   - 延迟双删缓解并发脏数据。
   - Canal/CDC 异步删缓存。
2. Redis 自身：
   - 主从复制、哨兵/集群；`WAIT` 可提升写安全但有代价。
   - AOF/RDB 持久化防重启丢失（非跨系统一致）。
3. 对账补偿。

**【示例/写法】**
update DB; deleteCache(key); // Cache-Aside 写路径

**【易错点】**
- 「双写同时成功」当强一致。
- 先写缓存再写 DB 导致脏读放大。

**【权威依据】**
- Redis Replication / Persistence
- Cache-Aside 模式（Microsoft 云架构模式等经典描述）

### Q048（原始编号: 70, 208）

**【题干】**
服务产生大面积雪崩问题的解决办法。

**【核心结论】**
雪崩指缓存大面积失效或缓存层宕机导致流量压垮 DB/下游。手段：过期打散、高可用、限流降级、舱壁隔离、多级缓存、预热。

**【详细说明】**
1. TTL 随机抖动，避免同一时刻过期。
2. Redis 集群/哨兵，避免单点。
3. 接口限流、熔断、线程池隔离。
4. 本地缓存（Caffeine）作二级。
5. 核心数据永不过期+异步刷新。
6. 过载保护与应急开关。
服务雪崩（微服务）还要靠熔断与重试退避。

**【示例/写法】**
TTL = base + random(0, jitter);

**【易错点】**
- 只加机器不限流。

**【权威依据】**
- Redis 过期策略；微服务弹性模式（熔断）

### Q052（原始编号: 125, 132）

**【题干】**
Redis 分布式锁。

**【核心结论】**
常用 SET key value NX EX 原子加锁；释放用校验唯一 value 的 Lua 删键；注意误删、锁续期（看门狗）、集群红锁争议与业务容忍度。

**【详细说明】**
要点：
1. 加锁：`SET lockId token NX EX seconds`。
2. 解锁：仅持有者可删（Lua 比较 token）。
3. 续期：业务长则 Redisson watchdog 或分段。
4. 集群：单实例锁在故障切换可能丢；Redlock 有争议，需评估。
5. 不可重入需自行实现或用 Redisson。

**【示例/写法】**
-- Lua unlock
if redis.call('get',KEYS[1])==ARGV[1] then return redis.call('del',KEYS[1]) else return 0 end

**【易错点】**
- 先 GET 再 SETNX 非原子。
- DEL 不校验持有者。
- 锁过期短过业务时间。

**【权威依据】**
- Redis SET 命令文档（NX EX）
- Redis 分布式锁释义（官方 blog「Correct implementation of distributed locks」）
- Redisson 文档

### Q055（原始编号: 156）

**【题干】**
Integer 缓存机制。

**【核心结论】**
Java 对 Integer 在常用范围（默认 -128~127）使用 IntegerCache 缓存装箱对象，该范围内 == 可能为 true；范围外各 new，== 为 false。应用比较应使用 equals。

**【详细说明】**
- `Integer.valueOf(int)` 使用缓存；`new Integer` 不走缓存（已弃用构造）。
- 范围可用 `-Djava.lang.Integer.IntegerCache.high` 调整上界。
- 与面试「缓存」主题不同，这是 JVM/语言级装箱缓存。

**【示例/写法】**
Integer a=127,b=127; // a==b true
Integer c=128,d=128; // c==d false
a.equals(b) // 应用应 equals

**【易错点】**
- 用 == 比较业务 Integer。
- 与 Redis 缓存混淆。

**【权威依据】**
- Java Language Specification 装箱；OpenJDK Integer.valueOf 源码/Javadoc

### Q056（原始编号: 182）

**【题干】**
Redis 默认使用哪种持久化方式？

**【核心结论】**
默认配置下 RDB 快照策略以 save 点形式存在（若未改 conf）；AOF 默认关闭（`appendonly no`）。具体以发行版 redis.conf 为准；生产常开 AOF 或混合。

**【详细说明】**
说明默认不等于生产推荐；解释 RDB 触发条件与 AOF 开关。Redis 7 等版本以官方发行 conf 为准核对。

**【示例/写法】**
grep appendonly redis.conf
grep '^save' redis.conf

**【易错点】**
- 绝对说「默认一定是 RDB」而不提版本/发行裁剪。

**【权威依据】**
- Redis 官方 redis.conf 与 Persistence 文档
