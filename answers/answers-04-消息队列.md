### Q057（原始编号: 60, 79, 114, 138, 214）

**【题干】**
消息队列（Message Queue，MQ）怎么保证消息一致性？

**【核心结论】**
「消息一致性」通常指：生产不丢、消费不重复副作用、与业务数据最终一致。手段：本地消息表/事务消息、确认机制、幂等消费、重试与死信、对账。

**【详细说明】**
1. 生产端：先写业务库与出箱表同事务，再异步投递；或 RocketMQ 事务消息。
2. Broker：持久化、多副本、ACK。
3. 消费端：幂等键（唯一约束/状态机）；失败重试；死信告警。
4. 对账补偿。
一致性是最终一致为主；跨库 2PC 成本高少用。

**【示例/写法】**
业务事务提交 → 扫 outbox → send MQ → 标记已发送
消费者：INSERT 幂等表成功才做业务

**【易错点】**
- 只开事务消息不谈消费幂等。

**【权威依据】**
- RocketMQ 事务消息文档
- Kafka at-least-once / idempotent producer
- 《企业集成模式》消息相关章节

### Q059（原始编号: 139）

**【题干】**
消息队列怎么保证数据一致性？比如最终消费金额都是 50 元，不会导致问题。

**【核心结论】**
金额类靠：事务消息/出箱保证「业务发生则消息必达」；消费幂等与状态机保证「只生效一次」；对账保证「最终金额正确」。

**【详细说明】**
示例：扣款 50 元：
1. DB 扣款与出箱同事务。
2. 消息带扣款单号与金额。
3. 消费者按单号幂等，重复消息不二次扣。
4. 日终对账。

**【示例/写法】**
唯一键：deduct_id；UPDATE ... WHERE status=INIT

**【易错点】**
- 用「正好一次」口头保证却无幂等。

**【权威依据】**
- 同 Q057；支付状态机实践

### Q060（原始编号: 150）

**【题干】**
消息队列用于解耦时，怎么保证业务和数据的一致性？

**【核心结论】**
解耦后一致性靠领域事件 + 可靠投递 + 幂等 + 补偿；明确权威数据源与最终一致窗口。

**【详细说明】**
流程同出箱模式；定义可重试业务操作；避免消费者直接改多个权威源无序。

**【示例/写法】**
订单服务发 OrderPaid；库存/积分订阅。

**【易错点】**
- 双向强耦合 RPC 又套 MQ。

**【权威依据】**
- 可靠事件投递模式
