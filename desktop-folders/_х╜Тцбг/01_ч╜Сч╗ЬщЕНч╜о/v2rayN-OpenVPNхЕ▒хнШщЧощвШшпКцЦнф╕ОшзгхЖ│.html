v2rayN（TUN 模式翻墙）与 OpenVPN（访问内网）共存问题
诊断与解决方案

生成日期：2026-08-09 ｜ 适用环境：Windows 11 x64 ｜ 客户端：OpenVPN Connect 3.8 + v2rayN 7.24.3（sing-box 内核）

一、问题概述

同时开启 v2rayN（TUN 模式，全局代理翻墙）与 OpenVPN（访问腾讯云服务器内网）时，出现冲突：

  • 开启 OpenVPN 后，无法访问 YouTube 等境外网站（域名解析超时）；
  • 内网流量被 v2rayN 的 TUN 虚拟网卡"抢走"，无法到达 OpenVPN 隧道。

两者都在争夺系统的"默认路由"与"DNS 解析"，需要正确分流才能共存。

二、一句话原因

OpenVPN Connect 客户端强制开启"DNS 泄漏防护"，连接时通过 Windows 过滤平台（WFP）屏蔽了除自身之外所有应用的 DNS 查询（端口 53），导致 v2rayN 的 sing-box 内核无法解析域名，境外网站因此打不开。

三、详细原因分析

1. 流量分流原理

  • v2rayN（sing-box TUN 模式）：创建虚拟网卡（singbox_tun）接管默认路由 0.0.0.0/0，使用 dns_mode: hijack 劫持 DNS 查询做域名分流，匹配规则（如 geosite-google）后走代理。
  • OpenVPN：建立隧道后按"服务器推送的路由"接管流量。若未做限制，会连同 redirect-gateway 一起接管全部出口流量。

2. 冲突的两个根源

  1. 默认路由冲突：OpenVPN 服务器推送 redirect-gateway def1，与 v2rayN TUN 的默认路由互相争夺全局流量。
  2. DNS 泄漏防护冲突（根因）：OpenVPN Connect 3.x 的客户端 agent 服务在每次连接时，强制创建 WFP 过滤规则，屏蔽"其它应用"的 DNS 请求：
permit IPv4 requests from OpenVPN app
permit IPv6 requests from OpenVPN app
block IPv4 DNS requests from other apps     ← 屏蔽其它应用的 DNS
block IPv6 DNS requests from other apps
block IPv4 DNS requests to loopback from other apps  ← 连 127.0.0.1 都屏蔽
block IPv6 DNS requests to loopback from other apps

这条屏蔽规则与 OpenVPN 的 block-outside-dns 指令等价（官方手册明确说明其使用 WFP 阻止端口 53）。结果是 v2rayN 的 sing-box 进程无法向上游 DNS 服务器（如 223.5.5.5）或本地解析器发起查询，域名解析失败 → 连接超时 → 打不开境外网站。

3. 为什么"关不掉"（实测证据）

依次尝试了 3 种关闭方式，全部无效，日志为证：
  1. 删除 ovpn 中的 block-outside-dns 指令 → 连接日志仍出现上述 block 规则；
  2. 添加 pull-filter ignore "block-outside-dns" → 无效，客户端强制创建；
  3. 修改配置文件 allowLocalDnsResolvers=true → OpenVPN core 内部仍记录为 false（该设置为隐藏项 isAllowLocalDnsResolversVisible=false，未被采用）。

关键日志对比：OpenVPN core 层面已是 block_outside_dns : false，但 agent 仍无条件创建屏蔽规则。结论：OpenVPN Connect 3.8 的 DNS 泄漏防护为强制功能，客户端层面无法关闭。

四、诊断证据（实测数据）

定位结论：差异在于 DNS 解析路径。走 socks 代理时域名由远端解析（本地不发 DNS 查询，不被屏蔽）；走 TUN 时浏览器/应用需先本地解析域名，查询被 WFP 屏蔽 → 超时。

五、多种解决方案

方案一（推荐，已实测通过）：改用社区版 OpenVPN GUI

推荐社区版 OpenVPN（官网免费版）尊重 ovpn 配置文件，只有配置中显式写 block-outside-dns 才启用 DNS 屏蔽，否则不创建任何 WFP 规则，因此天然与 v2rayN TUN 共存。

  1. 下载安装：openvpn.net/community-downloads（Windows 选最新版，如 OpenVPN 2.6.x / 2.7.x）
  2. 把修改后的 .ovpn 放入 C:\Program Files\OpenVPN\config\
  3. 以管理员身份运行 OpenVPN GUI → 托盘图标右键 → 连接对应配置

关键 ovpn 配置（本方案核心）：

client
proto udp
explicit-exit-notify
remote 8.138.84.226 1194
pull-filter ignore "redirect-gateway"     # 不接管全局流量，只走内网路由
pull-filter ignore "block-outside-dns"    # 忽略服务器推送的 DNS 屏蔽
pull-filter ignore "dhcp-option DNS"      # 不让 OpenVPN 改系统 DNS
route 172.28.0.0 255.255.0.0              # 内网网段走 VPN（按实际网段调整）
dev tun
# ……证书部分省略……
# 注意：不要写 setenv opt block-outside-dns / block-outside-dns

效果：内网流量命中 OpenVPN 路由走隧道；境外流量走系统默认路由 → v2rayN TUN → 代理；互不干扰。

方案二：OpenVPN Connect 中开启"允许本地 DNS 解析器"

视版本支持OpenVPN Connect 设置文档中列有官方选项 "Allow using local DNS resolvers"（允许向本地解析器 127.0.0.1/::1 发送 DNS）。若你的版本界面可见该选项，开启后 v2rayN 的本地 DNS 查询可能不再被屏蔽。但在 3.8 版本中该选项为隐藏项，配置文件修改未生效。

参考：OpenVPN Connect 设置文档（官方）

方案三：v2rayN 改用"系统代理"模式（不开 TUN）

部分适用关闭 TUN，让 v2rayN 走系统代理。浏览器等走代理的程序翻墙正常；内网访问命中系统代理的直连例外列表 → 直连 → OpenVPN 隧道。缺点：仅对走代理的程序生效，命令行等非代理应用不受益。

方案四：手动添加防火墙放行规则

不保证为 sing-box 进程添加出站放行规则（UDP/TCP 53 端口），试图覆盖 OpenVPN 的 block。风险：OpenVPN 的规则位于 WFP 底层，放行规则优先级可能不足，且每次连接重建，需保持规则持久。

方案五：两客户端不同时开启

功能受限需要内网时连 OpenVPN，需要翻墙时开 v2rayN，不同时使用。最简单但无法同时满足需求。

六、本次实施方案与验证结果

采用：方案一（社区版 OpenVPN GUI）

  1. 用 winget 安装社区版 OpenVPN：winget install OpenVPNTechnologies.OpenVPN（安装 2.7.5，含 OpenVPN GUI、DCO 驱动、服务）；
  2. 修正 ovpn 配置（移除会报错的 ignore-unknown-option，保留三条 pull-filter 与内网路由）；
  3. 部署至 C:\Program Files\OpenVPN\config\；
  4. OpenVPN GUI 连接 yrg813884226（8.138.84.226）。
