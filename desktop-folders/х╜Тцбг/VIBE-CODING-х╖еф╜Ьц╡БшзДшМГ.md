## 一、项目启动协议

开始一个新项目（或接手一个已有项目）时，在项目根目录创建 `.project/` 目录：

```
.project/
  PROJECT.md          # 项目概述
  ROADMAP.md          # 路线图与任务清单
  CHANGELOG.md        # 变更日志
  sessions/           # 对话摘要存档
    session-YYYY-MM-DD-HH.md
```

### PROJECT.md 模板

```markdown
# 项目名称

## 一句话描述
[用一句话说清楚这个项目是做什么的]

## 技术栈
- 语言：
- 框架：
- 数据库：
- 部署：

## 核心目标
1. [目标1]
2. [目标2]

## 边界（不做什么）
- [明确排除的范围]

## 关键约束
- [性能/安全/兼容性等硬约束]
```

### ROADMAP.md 模板

```markdown
# 路线图

## 进度总览
- 总任务数：X | 已完成：Y | 完成度：Z%

## 里程碑 1：[名称] — [目标日期]
- [x] 任务1：描述
- [ ] 任务2：描述
- [ ] 任务3：描述

## 里程碑 2：[名称] — [目标日期]
- [ ] 任务4：描述
- [ ] 任务5：描述
```

### CHANGELOG.md 模板

```markdown
# 变更日志

## [日期] Session [编号]
### 任务：[任务名称]
- **修改文件：** `src/xxx.ts` — [改了什么，为什么改]
- **修改文件：** `src/yyy.ts` — [改了什么，为什么改]
- **新增文件：** `src/zzz.ts` — [是什么，为什么需要]
### 影响范围：[受影响的功能/模块]
```

> **小项目可以简化**：只用 PROJECT.md 写几行概述即可，不必全套启用。

## 二、任务管理流程

### 2.1 任务粒度原则

```
单次对话 = 1 个可验证的任务
```

**好的任务粒度：**
- "实现用户登录 API"
- "修复购物车数量不更新的 bug"
- "给 Table 组件添加排序功能"

**过大的任务（需要拆分）：**
- "完成整个用户系统" → 拆成：注册、登录、权限、个人信息...
- "重构整个前端" → 拆成：按模块逐个重构

### 2.2 对话开场协议

每次对话开始处理任务时，AI 必须先输出：

```
📋 当前任务：[任务描述]
🎯 目标：[本次要达成的具体结果]
📁 预计涉及：[文件/模块列表]
🚫 不做：[明确排除的范围]
```

用户确认后再开始编码。

### 2.3 任务状态机

```
planned → in_progress → review → done
                ↓
             blocked（记录阻塞原因）
```

任务完成时，更新 ROADMAP.md 中对应的 checkbox。

### 2.4 完成检查清单

任务完成前，AI 自检：

- [ ] 代码能运行/编译通过吗？
- [ ] 只改了计划内的文件吗？
- [ ] 有没有引入新的依赖？（如有，是否必要？）
- [ ] 有没有破坏现有功能？
- [ ] CHANGELOG.md 更新了吗？
- [ ] ROADMAP.md 的 checkbox 勾上了吗？

## 三、变更追踪机制

### 3.1 修改前：声明意图

每次修改文件之前，AI 必须说明：

```
✏️ 准备修改 `src/auth/login.ts`
   原因：添加 token 过期检查逻辑
   改动范围：第 45-60 行，新增 validateToken 函数
```

### 3.2 修改后：变更摘要

每个文件修改完成后，输出简明摘要：

```
✅ `src/auth/login.ts`
   + 新增 validateToken() 函数 (15行)
   ~ 修改 login() 函数：增加 token 验证调用
```

### 3.3 禁止静默修改

以下行为被明确禁止：

- **不碰任务范围外的文件**（除非修复直接关联的编译/运行错误）
- **不做顺手重构**（"既然打开了这个文件，顺便优化一下..."）
- **不加未要求的功能**（"我觉得加个缓存会更好..."）
- **不改代码风格**（添加注释、调整格式、改变量名等）

如果确实发现了应该改但不在范围内的问题，记录到待办，不要直接改：

```
📝 发现问题（不在本次范围）：
   - `src/utils.ts:23` 有潜在的空指针问题
   - 建议后续处理
```

### 3.4 对话结束时的变更总结

每次对话结束前，AI 必须输出完整的变更总结：

```
📊 本次变更总结
━━━━━━━━━━━━━━━━━━━━━━━━━━━━
修改文件：3 个 | 新增文件：1 个 | 删除文件：0 个

文件明细：
  ~ src/auth/login.ts      (+15, -3)  添加 token 验证
  ~ src/auth/middleware.ts  (+8, -2)   更新中间件调用
  ~ src/types/auth.ts       (+5, -0)   新增 Token 类型定义
  + src/auth/validator.ts   (+45)      新增验证器模块

未完成/遗留：
  - Token 刷新逻辑待下次实现
  - 发现 utils.ts:23 有空指针风险（非本次范围）
```

同时追加到 `.project/CHANGELOG.md`。

## 四、防跑偏机制

### 4.1 范围锁定

对话开始时声明的任务范围是"合同"——AI 不能单方面扩大范围。

**触发确认的情况：**
- 需要修改计划外的文件
- 需要引入新的依赖/库
- 发现需要改动的范围比预期大很多
- 需要修改公共/共享模块

此时 AI 应暂停并确认：

```
⚠️ 范围变更提醒
原计划只修改 auth 模块，但发现需要同时修改：
- src/middleware/cors.ts（跨域配置需要调整）
- package.json（需要添加 jsonwebtoken 依赖）

是否继续？还是先完成原计划部分？
```

### 4.2 长任务中途检查点

如果一个任务需要修改 **5 个以上文件**，AI 应设置检查点：

```
🔖 检查点 [2/4]
已完成：
  ✅ 数据库 schema 更新
  ✅ API 路由定义
进行中：
  🔄 Service 层逻辑
待做：
  ⬜ 前端对接

当前方向是否正确？继续？
```

### 4.3 复杂度预警

当 AI 发现任务比预期复杂时，应主动预警而不是硬做：

```
⚠️ 复杂度预警
原以为只需修改 1 个文件，实际发现涉及 8 个文件的联动修改。
建议：
  方案A：拆成 3 个小任务分步完成
  方案B：简化方案，先实现核心功能
  方案C：按原计划继续（风险较高）
你倾向哪个？
```

每完成一个任务，立即更新 ROADMAP.md：

```markdown
## 进度总览
- 总任务数：12 | 已完成：5 | 完成度：41.7%
- ████░░░░░░ 41.7%

```
📈 项目进度

### 5.3 适配不同项目规模

| 规模 | 启用项 |

| 大型项目（持续迭代） | 全套 + 里程碑管理 + session 归档 |

## 六、上下文接力

### 6.1 对话结束协议

每次对话结束时，AI 生成 session 摘要并保存到 `.project/sessions/`：

```markdown
# Session 摘要 — 2026-03-18 14:00

## 完成了什么
- 实现了用户登录 API
- 添加了 JWT token 验证中间件

## 未完成 / 遗留
- Token 刷新接口未实现
- 发现 CORS 配置需要调整

## 关键决策
- 选择 JWT 而非 Session 方案（原因：前后端分离架构）
- Token 有效期设为 24h

## 当前状态
- 分支：feature/auth
- 可运行：是
- 测试：3 passed, 1 skipped

## 下次继续
1. 实现 token 刷新接口
2. 处理 CORS 配置
```

### 6.2 新对话启动协议

新对话开始时，AI 应：

1. 读取 `.project/PROJECT.md` 了解项目概况
2. 读取 `.project/ROADMAP.md` 了解当前进度
3. 读取最近的 session 摘要了解上次做到哪里
4. 输出上下文概要：

```
📖 上下文恢复
上次对话（3月18日 14:00）完成了用户登录 API。
当前进度：里程碑1 完成 80%。
本次建议继续：Token 刷新接口。
```

### 6.3 与现有 memory 系统集成

- `.project/` 是**项目级**上下文（跟着项目走）
- `memory/` 是**全局级**上下文（跟着用户走）
- 两者互补，不重复

## 七、Claude Code 自动审批配置

Vibe Coding 的核心体验是**流畅不打断**。每次弹出权限确认都会打断心流。
以下配置让 Claude Code 在安全范围内自动执行代码操作，无需逐条审批。

### 7.1 权限模式一览

| 模式 | 说明 | 适用场景 |
|------|------|----------|
| `default` | 每个工具调用都要确认 | 初次使用、不信任环境 |
| `auto-edit` | 自动读写文件，命令仍需确认 | 日常开发（推荐起步） |
| `full-auto` | 自动执行所有操作（含命令） | Vibe Coding 全速模式 |

### 7.2 推荐配置：auto-edit 模式

适合大多数场景——文件读写自动化，shell 命令仍需确认，安全与效率兼顾。

**启动方式：**
```bash
claude --dangerously-skip-permissions
```

或在对话中输入：
```
/permissions
```
然后选择对应模式。

### 7.3 进阶配置：allowedTools（精细控制）

在 `.claude/settings.json`（全局）或项目的 `.claude/settings.local.json` 中配置：

```jsonc
// .claude/settings.json — 全局配置示例
{
  "permissions": {
    "allow": [
      "Read",          // 读取文件
      "Write",         // 写入文件
      "Edit",          // 编辑文件
      "Glob",          // 搜索文件
      "Grep",          // 搜索内容
      "Bash(npm run *)",       // 允许 npm 脚本
      "Bash(npx *)",           // 允许 npx
      "Bash(git status)",      // 允许 git status
      "Bash(git diff*)",       // 允许 git diff
      "Bash(git log*)",        // 允许 git log
      "Bash(git add *)",       // 允许 git add
      "Bash(git commit*)",     // 允许 git commit
      "Bash(ls *)",            // 允许 ls
      "Bash(cat *)",           // 允许 cat
      "Bash(mkdir *)"          // 允许 mkdir
    ],
    "deny": [
      "Bash(rm -rf *)",       // 禁止递归删除
      "Bash(git push --force*)", // 禁止强推
      "Bash(git reset --hard*)"  // 禁止硬重置
    ]
  }
}
```

### 7.4 项目级配置示例

在项目根目录创建 `.claude/settings.local.json`（不提交到 git）：

```jsonc
// 项目/.claude/settings.local.json
{
  "permissions": {
    "allow": [
      "Read", "Write", "Edit", "Glob", "Grep",
      "Bash(npm *)",
      "Bash(pnpm *)",
      "Bash(bun *)",
      "Bash(git *)",
      "Bash(node *)",
      "Bash(tsc *)",
      "Bash(eslint *)",
      "Bash(prettier *)"
    ],
    "deny": [
      "Bash(rm -rf /)*",
      "Bash(git push --force*)",
      "Bash(DROP TABLE*)"
    ]
  }
}
```

### 7.5 Vibe Coding 全速模式

如果你完全信任 AI 在当前项目中的操作（个人项目、实验性项目）：

```bash
# 启动时跳过所有权限检查
claude --dangerously-skip-permissions

# 或在 settings.json 中设置
{
  "permissions": {
    "allow": ["*"]
  }
}
```

> **注意**：全速模式下 AI 可以执行任何命令。建议仅在以下场景使用：
> - 个人实验项目
> - 有 git 版本控制兜底
> - 在 Docker/沙箱环境中

### 7.6 安全建议

| 级别 | 配置 | 建议场景 |
|------|------|----------|
| 保守 | 默认（不配置 allow） | 生产环境、团队协作 |
| 平衡 | allow 文件操作 + 常用命令 | 日常开发（推荐） |
| 激进 | `--dangerously-skip-permissions` | 个人实验、沙箱环境 |

**无论哪种模式，都建议：**
- 确保项目有 git 版本控制（可以随时回退）
- 重要操作前手动 `git commit`
- 不在 allow 中放 `rm -rf`、`DROP` 等破坏性命令

## 八、快速参考卡片

### AI 每次对话必做清单

```
开始时：
  □ 读取 .project/ 了解项目和进度
  □ 读取最近 session 摘要
  □ 声明本次任务范围
  □ 等用户确认后再动手

过程中：
  □ 修改前声明意图
  □ 修改后输出摘要
  □ 不碰范围外的文件
  □ 长任务设置检查点

结束时：
  □ 输出变更总结
  □ 更新 CHANGELOG.md
  □ 更新 ROADMAP.md
  □ 生成 session 摘要
  □ 输出进度报告
  □ 建议下次继续的方向
```

## 九、用户常用指令

| 指令 | 含义 |
|------|------|

## 十、规范的使用方式

1. **新项目**：告诉 AI "按 VIBE-CODING 规范初始化项目"，自动创建 `.project/` 目录
2. **已有项目**：告诉 AI "按 VIBE-CODING 规范接入"，AI 会分析现状并创建对应文件
3. **日常开发**：AI 会自动遵循变更追踪和进度更新流程
4. **切换对话**：新对话会自动读取上下文，无缝接力

> 这份规范的核心思想：**让 AI 像一个靠谱的初级开发者一样工作——接任务前确认范围，改代码前说明意图，改完后汇报结果，下班前写交接文档。**
