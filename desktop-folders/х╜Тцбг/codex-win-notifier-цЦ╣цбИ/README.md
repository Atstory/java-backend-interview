# Codex CLI Windows 完成通知方案

## 1. 背景结论

截至 2026-03-08，Codex CLI 官方存在通知相关配置，但不等于完整的原生 Windows 任务完成通知能力。

已确认的官方能力：

- `tui.notifications = true`
- `notify = ["agent-turn-complete"]`

这类能力更接近 CLI 内置桌面提醒，而不是面向 Windows 的可配置原生通知系统。并且官方对 Windows 的支持仍偏实验性，因此当前“任务完成后没有明显提示”是合理现象，不建议只依赖内置通知作为最终方案。

官方参考：

- Codex CLI：`https://developers.openai.com/codex/cli`
- Codex App Server：`https://developers.openai.com/codex/app-server`

## 2. 目标

实现一个面向 Windows 的 Codex 完成通知能力，满足以下要求：

- 对话或任务完成后给出系统级提示
- 通知自动关闭，默认 3 秒
- 用户可手动关闭
- 展示完成摘要详情
- 结构插件化
- 配置简单，后续便于扩展
- 第一阶段优先可落地，不强依赖修改 Codex CLI 内核

## 3. 方案对比

### 方案 A：直接启用 Codex CLI 内置通知

#### 核心逻辑

仅通过 Codex CLI 配置开启通知事件。

#### 优点

- 零开发成本
- 上手最快
- 升级成本最低

#### 缺点

- 无法保证满足“3 秒自动关闭 + 手动关闭 + 展示详情 + 插件化”
- Windows 下体验和稳定性不确定
- 可扩展性弱

#### 结论

只能作为兜底方案，不建议作为最终落地方案。

### 方案 B：CLI 外挂包装器

#### 核心逻辑

通过一个外部启动器包装 `codex` 命令，监听其输出，在识别到本轮完成后调用 Windows 通知能力进行展示。

#### 优点

- 不修改 Codex 内核
- 落地速度快
- 容易做成单文件
- 可快速实现 3 秒自动关闭与详情展示

#### 缺点

- 如果依赖文本匹配识别“完成”，会受 CLI 输出变化影响
- 稳定性不如事件流方案

#### 结论

适合作为第一版 MVP。

### 方案 C：基于 Codex App Server 的事件驱动通知器

#### 核心逻辑

接入 Codex App Server 的事件流或 JSON-RPC 通知，捕获任务完成、回合结束、状态更新等事件，再调用 Windows 原生通知。

#### 优点

- 识别完成状态更稳定
- 天然适合插件化
- 易于扩展多种通知渠道
- 更适合长期维护

#### 缺点

- 接入成本比包装器高
- 第一版开发复杂度更高

#### 结论

适合作为正式版和长期方案。

## 4. 推荐策略

采用“两阶段策略”：

### 第一阶段：先做方案 B

目标是尽快得到一个真正可用的 Windows 通知能力。

实现建议：

- 使用 PowerShell 单文件或 C# 单文件实现
- 以包装器方式启动 Codex CLI
- 监听输出并归纳本轮结果
- 触发 Windows Toast 或轻量弹窗

推荐优先级：

1. 原生 Toast 通知
2. 若 Toast 控制受限，则退化为轻量 WinForms 小窗

### 第二阶段：升级到方案 C

当第一版稳定后，再把“完成识别”从文本匹配切换为官方事件流驱动。

升级后的收益：

- 更稳定
- 更容易维护
- 更适合做插件体系

## 5. 推荐的第一版架构

虽然第一版只做一个文件，但逻辑上建议分成三个层次：

### 5.1 事件源适配器

职责：负责判断 Codex 是否完成。

可支持两种模式：

- `cli-output`：监听 CLI 输出
- `app-server`：监听官方事件流

第一版默认采用 `cli-output`。

### 5.2 通知渲染器

职责：将任务结果渲染成 Windows 通知内容。

建议展示字段：

- 标题：任务已完成
- 模型或会话标识
- 执行状态：成功 / 失败 / 中断
- 摘要：本轮完成内容
- 耗时
- 时间戳

### 5.3 配置中心

职责：统一管理通知行为。

建议配置项：

- `enabled`
- `mode`
- `autoCloseSeconds`
- `maxSummaryLength`
- `showDuration`
- `showTimestamp`
- `showStatus`
- `renderer`
- `keywords`

## 6. 第一版功能边界

第一版建议只做必要能力，不做过度设计。

包含：

- 启动 Codex CLI
- 监听当前运行结果
- 识别任务完成
- 弹出 Windows 通知
- 3 秒自动关闭
- 支持手动关闭
- 显示精简完成摘要
- 通过文件顶部配置区进行简单配置

暂不包含：

- 多渠道通知推送
- WebHook
- 企业微信 / 钉钉 / 飞书
- 数据库存储
- 多实例统一控制台
- GUI 配置界面

## 7. 为什么通知层建议优先选 Toast

选择 Toast 的原因：

- 更接近原生 Windows 体验
- 用户感知自然
- 不需要长期驻留窗口
- 与“任务完成提醒”场景匹配度高

需要注意：

- Toast 的按钮、超时与行为受系统机制约束
- 若需要绝对可控的 3 秒自动关闭窗口效果，WinForms 小窗更容易精确控制

因此推荐策略是：

- 默认优先 Toast
- 对“严格 3 秒消失”要求强时，使用自绘轻量小窗作为替代实现

## 8. 插件化设计建议

虽然第一版只做一个文件，但内部要预留插件化接口。

建议抽象为：

- `Get-EventAdapter`
- `Parse-CompletionEvent`
- `Build-NotificationPayload`
- `Show-Notification`
- `Load-NotifierConfig`

后续如果拆项目，可自然演进为：

- `adapters/`
- `renderers/`
- `plugins/`
- `config/`

这样不会推翻第一版实现。

## 10. 最终建议

从工程性、稳定性、实现成本三者平衡看：

- 立即落地：选择“CLI 包装器 + Windows 通知”
- 中期升级：切换到“App Server 事件驱动”
- 第一版实现语言：优先 PowerShell
- 第一版交付形态：单文件

这是当前最贴合你诉求、且风险最低的路径。
